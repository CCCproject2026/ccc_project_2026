# プロフィール表示・更新 詳細設計

更新日：2026-10-20 ／ 対象：ccc-249「自分のプロフィールを表示・更新できるページを実装する」

## 1. この機能でできること

ログイン中のスタッフ（NURSE・CAREGIVER）が、マイページ（`/profile`）で自分の情報を確認し、本人が管理すべき項目を更新できる。

現状のマイページは表示のみ（[新スタッフ登録 詳細設計](./01_新スタッフ登録詳細設計.md) 1節で「プロフィールの後からの編集は別Task」とした部分）。本Taskでその編集を追加する。
基本設計は [Web基本設計](../../basic_design/web_basic.md)、DBは [現行schema.prisma](../../../main/web/prisma/schema.prisma) に従う。
**DBの列・Enum・migrationは変更しない。**

### 対象外（別Task）

- NURSEが他のスタッフのプロフィールを編集すること（再招待時の入力更新は既存機能のまま）
- 入職日・退職日の編集、在職期間の履歴管理
- プロフィール画像

## 2. 必ず守るルール

- 本人が更新できるのは**自分の行だけ**。更新対象のIDはリクエストから受け取らず、ログイン情報（`requireStaff()`）から決める。
- 更新できるのは `ACTIVE` の本人だけ。PENDING・INACTIVEは画面もAPIも利用できない（既存の認可どおり）。
- ロール・利用状態・入職日・退職日・clerkUserIdは本人が変更できない。APIで送られても無視ではなく400とする。
- メールアドレスの正はClerk。DBのemailを本APIで直接書き換えない。
- DBに保存する値は英語のコード（性別は `MALE` / `FEMALE`）。日本語は画面表示だけに使う。
- 入力チェックは画面とサーバーで同じzodスキーマを使う。

## 3. 項目ごとの扱い

| 項目 | DB列 | 表示 | 本人による更新 | 更新方法 |
|---|---|---|---|---|
| 姓・名 | `lastName` / `firstName` | ○ | ○ | 本APIで更新 |
| 生年月日 | `dateOfBirth` | ○ | ○ | 本APIで更新 |
| 国籍 | `nationality` | ○ | ○ | 本APIで更新 |
| 性別 | `gender` | ○ | ○ | 本APIで更新 |
| メールアドレス | `email` | ○ | ○ | Clerkのアカウント画面で変更 → `user.updated` WebhookでDBへ同期（既存処理） |
| ロール | `role` | ○ | × | NURSEがスタッフ管理画面で変更 |
| 利用状態 | `status` | ○ | × | NURSEがスタッフ管理画面で変更 |
| 入職日 | `startDate` | ○ | × | 招待時の値。変更は別Task |
| 退職日 | `endDate` | 値があるときだけ | × | 別Task |

入職日・退職日は人事情報のため、本人ではなく管理者が扱う。
変更できない項目は、画面に「変更したい場合は管理者（看護師）に連絡してください」と表示する。

## 4. 処理の流れ

### 4.1 表示

1. `src/app/(authenticated)/profile/page.tsx` で `requireStaffPage()` を呼び、ログイン中のUserをDBから取得する（キャッシュしない）。
2. 表示用の `ProfileInfo` に変換して `ProfilePage` に渡す。clerkUserId・id・createdAt などは渡さない。
3. 編集フォームの初期値用に、日付は `YYYY-MM-DD`（`fromDbDate()`）も渡す。表示用の「2026年10月1日」形式（`formatJapaneseDate()`）とは別の項目にする。

### 4.2 プロフィール更新

1. 本人が「編集」を押すと、`FormModal` で編集フォームを開く。初期値は現在の値。
2. 「保存」で `PATCH /api/profile` を呼ぶ。
3. サーバーは `requireStaff()` で本人を特定し、入力を検証する。
4. `id = 本人のid` かつ `status = ACTIVE` を条件に、送られた5項目だけを更新する。
5. 更新0件なら（直前に無効化された等）403を返す。
6. 成功したら200と更新後の `ProfileInfo` を返す。画面は `router.refresh()` で再表示し、モーダルを閉じる。

### 4.3 メールアドレス変更

1. マイページの「アカウント情報を変更」で、Clerkのアカウント画面（`useClerk().openUserProfile()`）を開く。
2. 本人がClerkで新しいメールアドレスを追加・検証し、primaryに設定する。
3. Clerkの `user.updated` Webhookで、既存の同期処理（新スタッフ登録 詳細設計 7節）がDBのemailを更新する。

Webhookは非同期のため、変更直後のマイページには古いemailが表示されることがある。
画面に「反映まで少し時間がかかる場合があります」と表示する。
別Userとemailが衝突した場合は既存処理どおりDBを更新せず、運用通知を出す。

## 5. APIと入力

| Method | Path | 認可 | 入力 | 正常応答 |
|---|---|---|---|---|
| PATCH | `/api/profile` | `requireStaff()`（ACTIVEなら誰でも） | 下記の5項目 | 200：`{ profile: ProfileInfo }` |

パスに `:id` を持たない。自分以外を更新する手段をAPIに作らない。

### 入力ルール

新スタッフ登録の招待入力（`staff-input.ts`）と同じルールにする。

| 項目 | ルール |
|---|---|
| lastName / firstName | 必須。前後空白除去後1〜50文字 |
| dateOfBirth | `YYYY-MM-DD`の実在日。日本時間の本日より前 |
| nationality | 前後空白除去後1〜100文字 |
| gender | `MALE` / `FEMALE` のみ |

- 5項目すべて必須（部分更新はしない）。フォームは常に全項目を送る。
- 上記以外のキー（`email`・`role`・`status`・`startDate` など）が含まれていたら400（`z.object(...).strict()`）。
- スキーマは `staffInviteSchema.pick({ lastName, firstName, dateOfBirth, nationality, gender }).strict()` で作り、ルールを二重に書かない。
- 日付は `toDbDate()` でDate型に変換し、時差で日付をずらさない。

### エラーの返し方

既存の共通形式 `{ code, message }`（`errorResponse()`）を使う。

| HTTP | 意味 |
|---|---|
| 400 | 入力不正、更新できない項目が含まれる |
| 401 | 未ログイン |
| 403 | ACTIVEでない（更新中に無効化された場合も含む） |
| 500 | DBの予期しないエラー |

## 6. DB更新と同時操作

```ts
// 本人の行で、ACTIVE のときだけ更新する
const result = await prisma.user.updateMany({
  where: { id: loginUser.id, status: "ACTIVE" },
  data: { lastName, firstName, dateOfBirth, nationality, gender },
});
```

**スタッフ管理の共通ロック（新スタッフ登録 詳細設計 6節）は使わない。** 理由は次のとおり。

| 観点 | 判断 |
|---|---|
| Clerk呼び出し | なし。1件の条件付きUPDATEだけで完結する |
| 無効化との同時実行 | `status = ACTIVE` を条件にするため、無効化後の更新は0件になり403で終わる |
| ロール変更・email同期との同時実行 | 更新する列が重ならない |
| 再招待との同時実行 | 再招待はINACTIVE・未紐付けの行だけが対象。本人更新はACTIVEだけなので同じ行にならない |

本人が複数タブから同時に保存した場合は、後に届いた保存が残る（後勝ち）。本人だけが編集する項目のため許容する。

## 7. 画面

- `/profile`：現在の表示（名前カード＋スタッフ情報）に「編集」ボタンを追加する。
- 編集モーダル：姓・名・生年月日（date入力）・国籍・性別（ドロップダウン。表示は `GENDER_LABELS`）。
  react-hook-form ＋ zodResolver で、5節のスキーマをそのまま使う。
- メールアドレスの行に「変更」ボタン（4.3）。
- ロール・利用状態・入職日・退職日の行には編集ボタンを出さない。
- 保存中は保存ボタンを無効化する（`FormModal` の `isSubmitting`）。
- 保存失敗時はモーダルを閉じず、フォームの上にエラーメッセージを表示する（招待フォームと同じ形）。入力値は残す。
- 403が返った場合は、`/account-status` へ移動する。

## 9. ログ・個人情報

- 更新成功時に `{ type: "profile_update", at, actorId, targetId }` だけを出力する。
- 変更前後の氏名・生年月日・国籍・性別・emailはログに出さない。
- APIの応答には本人の情報だけを含める。clerkUserIdは返さない。
