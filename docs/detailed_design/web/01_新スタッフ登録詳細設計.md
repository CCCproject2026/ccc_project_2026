# 新スタッフ登録 詳細設計

更新日：2026-10-13 ／ 対象：[Issue #175](https://github.com/CCCproject2026/ccc_project_2026/issues/175)

## 1. この機能でできること

NURSEがスタッフを招待し、本人がClerkで登録するとシステムを利用できる。
NURSEは、招待の取消・登録の復旧・ロール変更・無効化・再有効化も行える。

基本設計は [Web基本設計](../../basic_design/web_basic.md)、DBは [現行schema.prisma](../../../main/web/prisma/schema.prisma) に従う。
DBの列・Enum・migrationは変更しない。プロフィールの後からの編集、本番の初期アカウント作成は別Taskとする。

### 元の設計から変える点

| 変更 | 理由 |
|---|---|
| 新規招待と、PENDINGの復旧を別のAPIにする | 「409で拒否」と「再実行で復旧」の矛盾をなくす |
| 無効化・有効化はDBだけで行う。Clerkのban/unbanは呼ばない | 本システムへのアクセスをDBで確実に拒否し、外部の停止・再開との競合をなくす |
| 既存Clerkアカウントは、NURSEが明示確認して紐付ける | 再招待しただけで自動的に本人扱いしない |
| 有効化時は氏名・email・ロールだけを表示する | プロフィール取得APIを増やさず、既存DTOで操作できるようにする |

**無効化後もClerkへのログイン自体は可能。ただし、本システムの画面・データ・業務APIは利用できない。**
Clerkセッション自体の失効が必要になった場合は、外部同期の運用を含めた別の要件として扱う。

## 2. 必ず守るルール

- ロールと利用状態の正はDB。認証情報とメールアドレスの正はClerk。
- スタッフ管理は、DBで `ACTIVE` かつ `NURSE` の人だけが操作できる。
- 通常の画面・データ取得・業務APIは、DBで `ACTIVE` の人だけが利用できる。
- Userは物理削除しない。同じ人を再利用するときは、同じUser行を使う。
- 最後のACTIVEなNURSEは、降格・無効化できない。
- 招待時に必須プロフィールをすべて入力する。`PENDING_PROFILE`は追加しない。
- 状態変更と外部APIの成功は別に扱う。タイムアウトを「何も起きなかった」と判断しない。

## 3. 状態と操作

| DBの状態 | clerkUserId | 意味 | 画面の主な操作 |
|---|---|---|---|
| `PENDING` | なし | 登録待ち。招待未送信・送信結果不明も含む | 照合、取消 |
| `ACTIVE` | あり | 利用可能 | ロール変更、無効化 |
| `INACTIVE` | なし | 招待取消・招待失敗など | 再招待、取消処理の再試行 |
| `INACTIVE` | あり | 利用停止中 | 有効化 |

`status`だけで「メール送信済み」「Clerkと同期済み」とは判断しない。
`syncStatus`などのDB列は追加せず、その操作の結果をAPI応答で返す。

| 操作 | 対象 | 成功後 | 失敗した場合 |
|---|---|---|---|
| 新規招待 | DBに同じemailがない | PENDING | 確実な送信失敗はINACTIVE、結果不明はPENDING |
| 照合 | PENDING | 招待を確認・送信。条件が揃えばACTIVE | PENDINGを維持し、再試行 |
| 取消 | PENDING、または未紐付けのINACTIVE | INACTIVE | DBはINACTIVEを維持し、Clerkの招待失効だけ再試行 |
| 再招待 | 未紐付けのINACTIVE | PENDING。自動紐付け条件を満たす場合はACTIVE | 確実な送信失敗はINACTIVE、結果不明はPENDING |
| 無効化 | ACTIVE、または紐付け済みのINACTIVE | INACTIVE | DB更新に失敗したら成功扱いにしない |
| 有効化 | 紐付け済みのINACTIVE | ACTIVE | アカウント確認・DB更新に失敗したらINACTIVEを維持 |
| ロール変更 | ACTIVE | 状態は変えない | ロールを変えない |

## 4. 処理の流れ

### 4.1 新規招待

1. NURSEがemail・ロール・姓・名・生年月日・国籍・性別・入職日を入力する。
2. サーバーは入力を検証し、全項目入りのUserをPENDINGで作る。
3. Clerkを確認する。既存アカウントがあれば自動では紐付けず、確認が必要な旨を返す。
4. 有効な招待があれば再送しない。なければ招待を作成する。
5. 本人がサインアップすると、WebhookでUserをACTIVEにする。

同じemailのUserが既にある場合、新規招待APIは409を返す。
PENDINGなら「照合」、INACTIVEなら「再招待／有効化」を案内する。

本システムで作るClerk招待には、サーバーから `publicMetadata.staffUserId = User.id` を付ける。
ロールはmetadataから取得せず、DBの値を使う。

### 4.2 照合：送信失敗・Webhook未到着からの復旧

NURSEがPENDINGの行で「照合」を押す。サーバーはClerkの最新情報を確認する。

| Clerk側の状態 | 処理 | result |
|---|---|---|
| 本システムの招待経由のアカウントがある | 下記の自動紐付け条件を確認し、ACTIVEにする | `LINKED` |
| 別経路の既存アカウントがある | 自動で紐付けず、NURSEに確認を求める | `CONFIRM_REQUIRED` |
| 本システムが発行した有効な招待がある | PENDINGを維持。新しいメールは送らない | `ALREADY_INVITED` |
| アカウントも有効な招待もない | 招待を作成する | `SENT` |
| 招待の作成が確実に失敗した | 再照合で自分の招待が見つからなければ失敗とする | `SEND_FAILED` |
| 招待の作成結果が不明（タイムアウト等） | PENDINGを維持。次回の照合で確認する | `SEND_UNKNOWN` |
| 候補が複数・別Userに紐付け済み・未検証email・利用不能・本システム以外の招待がある | 紐付けも送信もせず、手動確認を案内する | `MANUAL_CHECK_REQUIRED` |
| Clerkを確認できない | PENDINGを維持。送信せず再試行を案内する | `RETRY_REQUIRED` |

`SEND_FAILED`・`SEND_UNKNOWN`・`MANUAL_CHECK_REQUIRED` は実装時に追加した。呼び出し元（新規招待・再招待・照合）が、それぞれに合ったHTTP応答とDB状態を決められるようにするため。
`MANUAL_CHECK_REQUIRED` には理由（`MULTIPLE_ACCOUNTS` / `LINKED_TO_OTHER_STAFF` / `EMAIL_NOT_VERIFIED` / `ACCOUNT_UNUSABLE` / `FOREIGN_INVITATION`）を付ける。

自動紐付けには、①PENDING・未紐付け、②検証済みprimary emailの完全一致、③Clerkから取得した `publicMetadata.staffUserId` の一致、④他のUserに紐付いていないこと、のすべてが必要。
Clerkアカウントが停止・ロック中など利用不能ならACTIVEにせず、手動確認を案内する。

`/sync`から招待を送信した場合は、確実な送信失敗・結果不明のどちらもPENDINGを維持し、502と `retryAction: SYNC` を返す。新規招待・再招待の確実な送信失敗をINACTIVEにするルールとは区別する。

`CONFIRM_REQUIRED`では、NURSEに「このメールアドレスの既存アカウントへ、このスタッフの権限を付与する」と表示する。
NURSEが確認すると、サーバー発行の短期確認トークンを付けて照合APIを再実行する。
トークンは対象User・候補Clerk ID・email・UserのupdatedAt・確認者・有効期限5分に結び付けて署名する。
再実行時は署名・期限・権限とClerkの最新情報を再検証する。候補が変わった場合は409とし、確認し直す。
未検証email、複数候補、別Userへの紐付け済みは確認操作でも許可しない。

確認トークンは署名だけでなく暗号化も行い、候補Clerk IDなどの内部情報をクライアントから読めない形式にする。再実行時はサーバー側で復号し、改ざんされていないことも検証する。暗号鍵はサーバー側だけで管理する。

### 4.3 招待の取消・再招待

**取消：** DBを先にINACTIVEにし、その後、本システムが発行した同じUser向けの有効なClerk招待を失効させる。
既に受理・失効済みなら成功とする。APIエラー時は最新状態を再取得して判定し、確認できなければ502を返す。
INACTIVE・未紐付けの行でも同じ取消を再実行できる。

取消とサインアップが重なった場合、DBが既にACTIVEなら取消は409とし、無効化を案内する。
DBが先にINACTIVEになった場合、後からWebhookが届いてもACTIVEに戻さない。

**再招待：** 同じUser行の入力項目を更新してPENDINGに戻し、4.2と同じ照合を行う。
既存アカウントを見つけた場合も、同じ紐付け条件・確認手順を使う。

### 4.4 無効化・有効化・ロール変更

**無効化：** 最後のNURSEでないことを確認し、DBをINACTIVEにする。既にINACTIVE・紐付け済みなら200を返す。
Clerkの停止APIは呼ばないため、Clerk停止失敗の再試行は不要。

**有効化：** 保存済みclerkUserIdでClerkアカウントの存在と利用可否を確認し、DBをACTIVEにする。
プロフィール・ロールは保持し、emailは最新情報に同期する。email衝突やアカウント不在の場合は有効化しない。
ロールを変える場合は、有効化後にロール変更APIを使う。

**ロール変更：** ACTIVEのUserだけを対象にする。同じロールへの変更は200。
最後のNURSEをCAREGIVERへ変更する操作は403。

入職日・退職日は利用権限の判定に使わない。この操作ではendDateを変更しない。
在職期間の編集・履歴管理は別Taskとする。

## 5. APIと入力

下記のスタッフ管理APIは、すべて `requireRole('NURSE')` を通す。

| Method | Path（先頭は `/api/staff`） | 入力 | 正常応答 |
|---|---|---|---|
| GET | `/invitations` | なし | 200：PENDING一覧 |
| POST | `/invitations` | 招待入力一式 | 201：新規Userと処理結果 |
| POST | `/invitations/:id/sync` | `{ confirmationToken? }` | 200：Userと照合結果 |
| DELETE | `/invitations/:id` | なし | 200：INACTIVEのUser |
| POST | `/invitations/:id/reinvite` | 招待入力一式。emailは変更不可 | 200：Userと処理結果 |
| GET | `/` | `status?=ACTIVEまたはINACTIVE` | 200：スタッフ一覧 |
| PATCH | `/:id/role` | `{ role }` | 200：更新後のUser |
| DELETE | `/:id` | なし | 200：INACTIVEのUser |
| POST | `/:id/activate` | なし | 200：ACTIVEのUser |

新規招待で既存Clerkアカウントが見つかった場合も、作成したUserはPENDINGで保持し、201と `CONFIRM_REQUIRED` を返す。
「新規では拒否したが再招待なら自動で紐付く」という例外は設けない。

### 入力ルール

| 項目 | ルール |
|---|---|
| email | 必須。前後空白除去・小文字化・形式検証 |
| role | `NURSE` / `CAREGIVER` のみ |
| lastName / firstName | 必須。前後空白除去後1〜50文字 |
| dateOfBirth | `YYYY-MM-DD`の実在日。日本時間の本日より前 |
| startDate | `YYYY-MM-DD`の実在日 |
| nationality / gender | この版では自由入力。前後空白除去後1〜100文字 |

日付はDBのDate型に保存し、時差で日付をずらさない。クライアント検証に加え、サーバーでも同じ検証を行う。

### エラーの返し方

応答は `{ code, message, staff?, retryAction? }` とする。`staff`には下記DTOだけを含める。

| HTTP | 意味 |
|---|---|
| 400 | 入力不正 |
| 401 | 未ログイン |
| 403 | 権限不足、最後のNURSEの降格・無効化 |
| 404 | 対象Userなし |
| 409 | 対象状態が違う、email/clerkUserIdの重複、確認トークンの不一致 |
| 502 | Clerkの確実な失敗、タイムアウト、照合失敗。現在のDB状態と次の操作を返す |
| 503 | ロック取得失敗など、一時的に処理できない |

招待作成の結果不明はPENDINGのまま502・`retryAction: SYNC`。
再照合で有効な招待を確認できた場合は成功とし、再送しない。
重複防止を無効にする `ignoreExisting: true` は使わない。重複エラー時もClerkを再照合する。
失効済み招待が再作成を妨げる場合は、自動で制約を回避せず、運用確認を案内する。

## 6. DB更新と同時操作

スタッフ管理は低頻度のため、この版では**User更新処理を共通のロックで1件ずつ実行する**。
新規招待・照合・取消・再招待・有効化・無効化・ロール変更・Webhook・bootstrapで同じロックを使う。

実装はPostgreSQLのsession-level advisory lockを使用する。
`pg`の専用接続を借り、共通の固定キーでロックを取得する。Prismaの短いDBトランザクションとClerk呼び出しが終わるまで、その接続を保持する。
Prismaのプール経由でsession lockを取得しない。`finally`で解放し、解放確認に失敗した接続は破棄する。
本番（Heroku Postgres）では `pg` 接続にSSL設定が必要。

ロック用接続の切断・異常を検知した場合は、その操作を中止し、以降のDB更新・Clerk呼び出しを開始しない。実行中の未コミットのDBトランザクションはロールバックする。確定済みのDB更新は戻さず、外部処理の結果が不明なら次回の照合・取消再試行で確認する。HTTP応答が可能な場合は503を返す。

1. ロック取得後に、呼び出し元の権限と対象Userの状態を再確認する。
2. DB更新は短いトランザクションで行う。ClerkのHTTP呼び出しはDBトランザクションに含めない。
3. 状態変更は期待するstatus・clerkUserIdを条件に含め、更新0件なら読み直す。
4. NURSEの件数確認と降格・無効化を同じDBトランザクションで行う。
5. email・clerkUserIdの一意制約違反は、作成・更新・紐付けのすべてで扱う。

ロック取得は最大5秒、外部HTTPは1回5秒、処理全体は25秒を上限とする（Herokuのルーターが30秒で要求を打ち切るため）。
途中停止でも確定済みのDB状態は残る。Clerk側の結果は次回の照合で確認する。
タイムアウト後の外部処理までロックで中止できるわけではなく、メールの厳密な一回配信は保証しない。

取消後に遅れて招待が作られた場合に備え、10分ごと（Heroku Scheduler）の復旧処理でINACTIVE・未紐付けのUserを確認し、本システム発行の招待を失効させる。
復旧処理も同じロックを使い、対象ごとに再確認する。失敗はログと運用通知に残し、次回再試行する。
INACTIVEのUserを自動で有効化する処理は持たない。

## 7. Clerk Webhookとメール同期

`POST /api/webhooks/clerk` は生のリクエスト本文で署名を検証する。署名不正は400、DB変更なし。

| イベント | 処理 |
|---|---|
| `user.created` | Clerkから最新情報を取得し、4.2の自動紐付け条件を満たすPENDINGだけACTIVEにする |
| `user.updated` | clerkUserIdでUserを特定し、最新の検証済みprimary emailをDBへ同期する。未紐付けなら自動紐付け条件も確認する |
| その他 | 200で受け取り、処理しない |

既に紐付け済みのUserを、重複した `user.created` で作り直さない。
メール更新ではrole・statusを変更せず、INACTIVEを復帰させない。
古いイベントの値で上書きしないよう、共通ロック取得後にClerkの最新情報を取得する。

メールが別Userと衝突した場合は更新せず、200で受理し、運用通知と警告ログを残す。
これは「不一致の解消」ではなく「不一致の検知」とする。
担当者は双方の所有者を確認し、Clerk側で重複しない検証済みprimary emailへ修正後、Webhookを再送する。
退職者のDB行を消したり、別人のclerkUserIdへ付け替えたりしない。
解決まで該当emailでの自動紐付けは拒否し、既存ユーザーの認可はclerkUserIdを使う。

Clerk取得失敗・DB一時障害は5xxを返し、Webhookの再配信に任せる。
対象なし・取消済みは200。対象がないだけで新しいUserを作らない。

## 8. 画面とDTO

一覧は次の情報だけを返す。PrismaのUser全体は返さない。

```ts
type StaffItem = {
  id: string;
  email: string;
  displayName: string; // 姓 名
  role: 'NURSE' | 'CAREGIVER';
  status: 'PENDING' | 'ACTIVE' | 'INACTIVE';
  availableActions: string[];
};
```

操作結果は `{ staff: StaffItem, result, confirmationToken? }`。
一覧は `{ staff: StaffItem[] }` に統一する。内部のclerkUserId・生年月日・国籍・性別は返さない。

| 状態 | availableActions |
|---|---|
| PENDING | `SYNC`, `CANCEL` |
| ACTIVE | `CHANGE_ROLE`, `DEACTIVATE`。最後のNURSEでは降格・無効化を無効表示 |
| INACTIVE・未紐付け | `REINVITE`, `RETRY_CANCEL` |
| INACTIVE・紐付け済み | `ACTIVATE` |

- `/staff/invitations`：PENDING一覧、全項目入力の招待フォーム、照合・取消。
- `/staff`：ACTIVE／INACTIVE一覧、ロール変更・無効化・再招待・有効化。
- 既存アカウントの採用は、照合結果の確認ダイアログから実行する。
- 有効化画面は氏名・email・ロールだけを表示する。プロフィールの再入力は求めない。
- 操作後は一覧を再取得する。エラーでもDB状態が変わる場合があるため、成功時だけ更新しない。
- 取消の外部処理失敗はINACTIVE一覧に移して「取消処理を再試行」を表示する。再読み込み後も同じ操作を選べる。
- UIのボタン制御とは別に、APIで権限・状態を再検証する。

## 9. 認可・初期アカウント・実装先

`requireStaff()` はClerkのログインIDでDBを検索し、ACTIVE以外を拒否する。
`requireRole('NURSE')` はさらにDBのroleを確認する。利用状態・ロールをリクエスト間でキャッシュしない。
middlewareはログイン確認だけを行い、ページのデータ取得処理・業務API・Server Actionにも認可を置く。layoutだけに依存しない。
ログイン済みでも登録待ち・無効化済みなら、業務データを含まない案内画面を表示する。

開発用 `bootstrap:nurse` は本番で実行禁止。共通ロック内でACTIVEなNURSEがいないことを確認する。
指定したemailのDB行とClerkアカウントを照合し、途中失敗で残った同一対象だけを再利用する。
bootstrap入力は招待と同じ全必須項目に加え、email・パスワードを環境変数で指定する。未設定なら開始前に停止する。
再利用するClerkアカウントは検証済みprimary emailの一致を必須とする。
別Userへの紐付け・email不一致・Clerk利用不能は停止する。既存行の紐付けを上書きしない。
新規の場合はClerkアカウントを作り、全必須項目入りのACTIVE・NURSEとしてDBへ保存する。
パスワードは環境変数から読み、ログに出さない。Clerkのみ作成できた場合は、再実行で照合してDB保存を完了する。

ファイル配置は、機能に依存しない共通処理を `src/shared/lib/`、スタッフ管理固有の処理を `src/features/staff-management/` に置く。
`shared` から `features` を import しない。`server/` 配下のファイルは先頭で `server-only` を import する。

| 実装先 | 責務 |
|---|---|
| `src/shared/lib/env.ts` | 環境変数の検証（起動時に `src/instrumentation.ts` から実行） |
| `src/shared/lib/prisma.ts` | Prisma Client の共通インスタンス |
| `src/shared/lib/api-error.ts` | 共通エラー応答 `{ code, message, ...extra }` |
| `src/shared/lib/logger.ts` | 運用通知 |
| `src/shared/lib/auth.ts` | ACTIVE確認、NURSE確認（全機能で使用） |

技術はNext.js・TypeScript・Prisma・Clerk SDK・svix・react-hook-form・zodを使用する。
session lock用に `pg` とその型を追加する。復旧スクリプトはHeroku Schedulerに登録する。
`server-only` を含むファイルをスクリプトから読み込む場合は `tsx --conditions=react-server` で実行する。
必要な設定は `DATABASE_URL`、Clerkの公開鍵・秘密鍵・Webhook secret、確認トークン用のサーバー秘密鍵（`STAFF_TOKEN_SECRET`）、bootstrap入力値。
DB接続はsessionを維持できる直接接続を使う。秘密鍵・トークン・パスワード・プロフィールをログへ出さない。
操作ログには実行者ID・対象ID・操作・前後の状態・外部処理結果を残す。

## 10. 完了条件

| 確認すること | 期待結果 |
|---|---|
| 新規招待とサインアップ | 必須項目を保存し、招待経由の本人だけACTIVEになる |
| 同じemailを二重登録 | 409。Userを増やさない |

| 未送信・失効済み招待の復旧 | 有効な招待の有無を確認し、送信または運用確認へ分岐する |
| 既存Clerkアカウント | 自動条件を満たすか、NURSEの明示確認を経た場合だけ紐付く |
| 取消とWebhookが同時実行 | INACTIVEをWebhookで復帰させない |
| 取消失敗・プロセス停止 | INACTIVEを保持し、画面または定期処理で失効を再試行できる |

| 無効化・有効化の同時実行 | 直列に処理され、後に受理した操作のDB状態になる |
| NURSEの同時降格・無効化 | 最後の1人が残る。待機後に実行者の権限も再確認する |
| Webhook署名不正・重複・順序逆転 | 不正は400。重複作成・取消済みの復帰・古いemailへの巻き戻りを起こさない |
