# project-explainer

## 目的と適用範囲

このリポジトリについて、開発者が自分で設計判断できるように、実装を根拠として技術を説明する。アーキテクチャ、Web、DB、API、認証、AI/IoT、インフラ、領域間の連携、または指定コードの理由を尋ねられたときに使う。

これは読み取り専用の説明Skillである。コード、設定、DB、MQTT、Git、外部サービスを変更・起動・送信しない。実装依頼には、その領域用Skillを使う。

## 最初の判断

質問の対象を一つに絞り、関連しない領域へ広げない。複合質問だけは、依頼者がつなぎ目を求めている範囲で複数の資料を読む。

| 質問の中心 | 読む資料 | 実装の再確認先 |
| --- | --- | --- |
| 全体構成・コンポーネント・起動構成 | `references/architecture.md` | 関係する entry point と `docker-compose.yml` |
| Next.js、Clerk、画面、DB、Web API | `references/web-and-database.md` | 対象 route、service、`schema.prisma` |
| MQTT、センサー入力、モデル、health | `references/ai-and-iot.md` | 対象 `main/ai/app` と mock publisher |
| Web/AI/IoT 間の接続、変更影響、担当境界 | `references/integration.md` | 両端の実装と契約文書 |
| 指定された関数・クラス・ファイル | そのコードが属する資料だけ | 指定コード、呼出元、呼出先 |

「Clerkとは」のような用語質問は、まずその用語だけを説明する。利用者が必要としたときだけ、認証からDB認可までを接続して説明する。対象のコードや質問の指す範囲が曖昧なら、確認できる候補と不足しているファイル名を示し、推測で補わない。

次のような代表質問では、要求された範囲を次の出力で確認する。

| 質問 | 最小の説明範囲 | 図 |
| --- | --- | --- |
| 「Clerkとは？」 | Clerk、`getLoginUser`、`requireStaff` に限定し、DB上のACTIVE確認まで | 最小の認証・認可フロー |
| 「システム全体のArchitectureは？」 | Web、DB、MQTT、AI入力、Composeと未接続点 | 実装済み経路のarchitecture/data-flow |
| 「Databaseは？」 | Prisma model、relation、migrationのSQL制約、アクセスservice | 必要ならER diagram |
| 「FrontendからBackendへの流れは？」 | 対象画面、client APIまたはServer Component、route/service、認可、Prisma | request/response sequence |
| 「自分の担当と他領域はどう連携する？」 | 根拠のある担当情報、モジュール責務、共有契約、影響候補 | 必要ならcomponent relationship |
| 「このコードはなぜ必要？」 | 指定コード、呼出元・呼出先、守る不変条件、失敗時の影響 | 複数の非自明な処理段階がある場合のみ |

## 説明の作り方

必要な深さで止める。利用者が指定しなければ、概念とこのプロジェクトでの利用（Level 1–2）から始め、内部機構・設計比較（Level 3–4）は質問に必要な場合だけ加える。

1. **Concept** — 用語、必要な理由、責務を平易に定義する。
2. **Project implementation** — 実在するファイル、route、関数、クラスを挙げ、プロジェクト内での役割を説明する。
3. **Internal mechanism** — 入口から出口までの順序、データ形、検証、失敗時の分岐を追う。
4. **Engineering perspective** — 実装から読み取れる設計理由、利点、制約、代替案を区別して述べる。採用理由を記録から確認できない場合は「理由は未確認」とする。

初出の専門語は一文で定義する。一般的な仕組みとプロジェクト固有の事実を分け、短い実コード例または関数名で結び付ける。コードを行ごとに言い換えるだけで終わらせず、「何を守るための処理か」「変更するとどの境界に影響するか」を説明する。

## 領域間の説明

接続を説明するときは、接続元・接続先・目的・インターフェース/データ形式・認証/認可・失敗時の確認先を示す。変更影響は、実在する依存先だけを「影響候補」として示す。人名や担当者名は、リポジトリ内の明確な根拠がある場合だけ記載する。根拠がなければ、モジュール単位の責務に留める。

このシステムのAI出力はリスク候補であり、医学的診断や転倒の確定ではない。未接続の推論・結果配信・Web通知を、実装済みの経路として説明しない。

## 図

複数コンポーネント、非自明なデータフロー、認証、API往復、DB関係を理解しやすくする場合だけ Mermaid を使う。図は本文の事実を要約し、ノードと矢印ごとに根拠となる実装を確認する。

- 全体/依存関係: `flowchart`
- 時系列の要求・応答: `sequenceDiagram`
- Prisma の関係: `erDiagram`
- 認証・認可: `sequenceDiagram` または `flowchart`

未実装・未確認・将来案は実線の経路に入れない。必要なら `未実装` と明記して別ノードにし、実装済みと区別する。

## 証拠と限界

- 資料は調査を速くする索引であり、変更されうる。説明前に質問に関係する現在のコード、契約、設定を読む。
- ファイルパスに加え、可能なら関数名、クラス名、endpoint名を記す。
- 実装で確認した事実、文書上の記述、設計上の推測、未確認事項を明示的に分ける。文書と実装が違う場合は両方を示し、現行動作は実装を優先する。
- Secret、環境変数の値、個人情報、生のセンサーpayloadは引用しない。変数名やスキーマ名だけなら必要な範囲で示せる。
- ローカルLLMがリポジトリを読めない場合、資料にない詳細を創作しない。確認が必要なパスを提示し、利用者に該当部分の共有を求める。

## 回答の最小構成

通常は「結論 → 概念 → このプロジェクトでの実装 → 必要なら処理順/図 → 接続先と影響 → 確認済み根拠と未確認事項」の順にする。質問の範囲と理解度に応じて短くする。

実装内容を学ぶための報告には既存の `learning-oriented-explanation` を使う。このSkillは、変更前でも使えるプロジェクト横断の説明と境界の理解を担当する。
