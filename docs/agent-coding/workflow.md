# Agent開発ワークフロー

既存 [Taskから開発](../development/workflow.md) と [設計テンプレート](../templates/README.md) を使用する。

1. **要件分析**: Issue・受入条件・非対象・扱うデータ・承認済み範囲を整理する。
2. **リポジトリ調査**: Git状態、関連コード/依存/契約/既存テストを確認。推測を未確認と分ける。
3. **技術設計**: Basic/Detailed Designに責務、API、MQTT、モデル入出力、認証、障害時動作を書く。未合意契約は担当者が確認。
4. **実装計画**: 対象ファイル、依存順序、検証方法をImplementation/Test Planへ記録。独立作業だけ委任し、担当範囲を分ける。
5. **実装**: Next.js SpecialistまたはPython/FastAPI/ML/IoT Specialistを選ぶ。契約をまたぐ変更は両担当で確認。
6. **自己レビュー**: 実差分を読み、誤編集・Secret・互換性・不要変更を確認。
7. **自動検証**: [コマンド](commands.md) から必要分を実行し、exit code・失敗・未実行理由を記録。
8. **独立コードレビュー**: 別Agentまたは人間へ差分、目的、受入条件、検証記録を渡す。Reviewerは説明を鵜呑みにせずコードと証拠を再確認する。
9. **修正と再レビュー**: 指摘への対応と残存リスクを記録し、修正箇所を再検証する。
10. **人間の承認**: PR・検証・復旧方法を提示。mainのPRは最低1名レビュー。Merge/Deploy等の承認を明示する。
11. **Merge / Deploy**: 承認された対象/手順のみ実施。未承認ならレビュー可能なローカル成果物で停止。完了後は日本語8項目の技術解説を残す。

## 引継ぎの最小情報

Issue/受入条件、担当ファイル、入力/出力と単位、未決事項、変更差分、実行コマンド/結果、残存リスク、必要承認。共有ブランチを並行編集せず、必要なら担当者がworktreeを作る。契約決定前にFrontend/Backend/IoTの依存実装を並列化しない。

## Reviewerの出力

Severity（Critical/High/Medium/Low）、ファイル:行、問題、理由、発生シナリオ、推奨修正、学習ポイントを記載する。正確性・境界/異常・データ整合性・競合・認証/認可・privacy・性能・エラー・API/DB互換性・テスト品質・保守性・責務を確認する。根拠のない指摘を作らず、指摘なしでも対象範囲と未検証範囲を書く。

同一セッションで「Reviewerになった」と宣言するだけでは独立レビューにならない。ネイティブ委任不可なら新しいセッションにRoleと差分を明示読込させるか人間へ依頼し、実施前は未完了と記録する。
