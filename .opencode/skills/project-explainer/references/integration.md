## 事実として説明できる接続

### AI → Web Device API

`DeviceApiClient.lookup` は `GET /api/devices/by-code/{deviceCode}` を専用Bearer tokenで呼ぶ。Webの`requireDeviceToken`がtokenを検証し、`lookupDeviceByCode`がdevice codeとstatusを返す。失敗の調査はAI側の `DeviceApiClient` / `DeviceManager`、Web側route・token検証・Prisma query、契約文書の順で行う。

### MQTT → AI input

MQTT payloadは callback から有限Queueへ入り、単一Workerが検証する。Queue full・再接続・Device APIの異常は入力連続性に関わるため、受信件数だけで継続推論可能とは断定しない。連続Bufferの実装はまだない。

### Web UI → Web server → DB

画面が直接DBへ接続することは確認していない。Server Componentのserviceまたはroute handlerが認可を行い、Prisma queryがPostgreSQLへ到達する。具体的なrequest/responseは機能ごとに異なるため、該当featureのclient APIとrouteを読む。

## 変更影響の説明規則

変更の説明では、次を「確認が必要な依存先」として扱う。実装済みでない結果publish/Web通知を依存先として断定しない。

- MQTT topic/payloadの変更 → `sensor_json.py`、`SensorInputService`、mock publisher、将来のFirmware担当との合意。
- Device API schema/tokenの変更 → Web route、AI `DeviceApiClient`、`docs/contracts/device-api/`。
- Prisma model/migrationの変更 → Web service/route、DB制約、Composeのmigrate、既存データへの影響。
- Clerk/スタッフ認可の変更 → `shared/lib/auth.ts`、ページguard、API guard、staff/webhook処理。
- Window/特徴順/モデル成果物の変更 → manifest、preprocessing、推論、提供者との互換性確認。無断の再学習・Scaler再fitは不可。
